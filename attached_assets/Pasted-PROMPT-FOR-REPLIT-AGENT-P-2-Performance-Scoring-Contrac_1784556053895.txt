## Phase 2 — Deterministic Scoring Layer

The scoring truth must be generated by code, not AI.

### A. Comparable cohort rules

Never compare unrelated posts blindly.

At minimum, comparisons must respect:

* same account
* same platform
* compatible metric availability
* compatible snapshot maturity
* comparable analysis window

Do not mix a 24h post with a 7d post in the same scoring cohort without explicit normalization and maturity labeling.

Do not compare Instagram and TikTok directly unless a reviewed normalization model exists. Default to platform-specific baselines.

### B. Snapshot maturity

Use the most mature honest checkpoint available.

Preferred order:

1. 7d
2. 72h
3. 24h

Every scored result must expose its maturity:

* `MATURE_7D`
* `PROVISIONAL_72H`
* `EARLY_24H`

Do not silently treat early results as final.

The same post must not be counted multiple times through its 24h, 72h, and 7d snapshots. Select one checkpoint per post for a given scoring run.

### C. Self-baseline only

All scoring must compare against the customer’s own historical performance.

No global benchmarks.
No invented “good engagement rate.”
No cross-customer benchmarks.
No Dubai-market averages unless a later verified dataset explicitly supports them.

The baseline must be:

* account-specific
* platform-specific
* time-bounded
* built from comparable posts
* versioned or timestamped

Exclude the evaluated post from its own baseline where mathematically appropriate.

### D. Metric registry

Implement a reviewed metric registry that identifies:

* which metrics are available per platform
* numerator
* denominator
* minimum denominator requirements
* whether the metric is primary, secondary, or unavailable
* whether higher or lower is better
* null-handling rules

Examples may include:

* save rate
* share rate
* comment rate
* engagement per reach
* view-to-action rate
* click rate

These are examples only. Use only metrics genuinely populated in the selected real campaign.

A missing denominator returns unavailable, not zero.

### E. Scoring dimensions

Score only dimensions supported by real lineage:

* hook style
* content angle
* content type

`mixBucket` does not exist at post level in the current schema and must not be invented.

`plannedSlot` may be analyzed as a separate exploratory dimension only if the data is sufficient and the architect approves it.

For each dimension value, output:

* sample size
* posts included
* checkpoint maturity distribution
* primary metric
* baseline value
* dimension value
* absolute delta
* relative delta
* consistency across posts
* confidence level
* verdict
* evidence references

### F. Verdicts

Use these factual verdicts:

* `WINNING`
* `NEUTRAL`
* `UNDERPERFORMING`
* `TESTING`
* `UNKNOWN`

Rules:

* Fewer than 3 comparable posts: `TESTING`.
* No honest usable metric: `UNKNOWN`.
* A single viral post cannot create `WINNING`.
* A single failed post cannot create `UNDERPERFORMING`.
* Winning and underperforming require both meaningful effect and consistency.
* Exact reviewed thresholds must be config-driven and documented.
* Do not lower thresholds to force a winner.
* If evidence is mixed, return `NEUTRAL` or `TESTING`.

AI may not change these verdicts.

### G. Confounding analysis

The code layer must expose potential confounders, such as:

* the winning angle appears only in Reels
* the winning hook appears only at one posting time
* all high-performing posts use the founder’s face
* one post contributes most of the total result
* samples span different maturity checkpoints
* different dimensions overlap too strongly

Do not claim causation where only correlation exists.

If the winning result is driven by one outlier, downgrade confidence rather than hiding it.

### H. Persistence and query surface

Persist scoring runs append-only with:

* campaign ID
* account ID
* scoring run ID
* baseline timestamp
* evaluated window
* dimension
* dimension value
* verdict
* confidence
* sample size
* metric definition
* score details
* evidence post IDs
* evidence snapshot IDs

* scorer version

Expose query surfaces for:

* score for one hook
* score for one angle

Do not overwrite previous scorecards.

## Phase 3 — AI Performance Interpretation Under Contract

AI is valuable here, but it operates only after deterministic scoring is complete.

### A. AI input contract

The AI receives only:

* deterministic scorecards
* baseline details
* included post evidence
* relevant captions and hooks
* confounding signals
* maturity labels
* campaign/product grounding
* supported Watchtower events where relevant

Do not give it permission to calculate or replace scores.

### B. AI responsibilities

The AI may:

* explain the likely business meaning of a factual verdict
* identify patterns across captions, hooks, and creative approaches
* group semantically similar labels for interpretation
* distinguish whether the apparent winner may actually depend on format or hook
* propose the next controlled content experiment
* explain what additional evidence is needed

The AI must not:

* change `TESTING` into `WINNING`
* invent metrics
* invent customer reactions
* claim causation as fact
* use global benchmarks
* produce generic marketing advice
* recommend a fixed template
* hide insufficient evidence
* cite a post or metric that was not supplied

### C. Performance Interpretation Contract

Create or extend a formal contract requiring every interpretation to include:

1. **What is proven**

   * Exact code verdict.
   * Metric and delta.
   * Sample size.
   * Maturity.
   * Evidence post and snapshot references.

2. **What is only a hypothesis**

   * Clearly labeled.
   * Supported by observable content differences.
   * No causal language presented as fact.

3. **What could be confounding the result**

   * Format.
   * timing.
   * audience.
   * outlier.
   * hook/angle overlap.
   * insufficient maturity.

4. **What to test next**

   * One controlled experiment.
   * Change one major variable where possible.
   * Define what remains constant.
   * Define the measurement checkpoint.
   * Define what result would strengthen or weaken the hypothesis.

5. **Why this is specific to this campaign**

   * Reference the actual product, audience, angle, posts, and evidence.
   * It must not apply unchanged to a generic competitor.

### D. AI output judge

The judge must reject an interpretation if:

* it contradicts the deterministic verdict
* it omits evidence references
* it treats a hypothesis as proven
* it ignores sample-size weakness
* it gives generic advice
* it proposes the same test that could apply to any business
* it invents a reason for performance
* it recommends scaling a `TESTING` dimension as if proven
* it ignores identified confounders
* it uses unavailable metrics

Use the existing interchangeability pattern.

If rejected:

* regenerate within a strict retry limit
* log `PERFORMANCE_INTERPRETATION_REJECTED`
* include rejection reasons
* no retry storm

If all retries fail:

* show the deterministic scorecard only
* visibly mark interpretation as unavailable
* never use a silent template fallback

### E. No template disease

Do not generate fixed skeleton recommendations such as:

* “Create 3 more posts using the winning angle.”
* “Post more educational content.”
* “Use stronger hooks.”
* “Double down on what works.”

The next experiment must come from the actual evidence.

Example of acceptable specificity:

“The proof-angle posts are currently 28% above this account’s Instagram baseline, but all three also use founder-led opening shots. Test the same customer-result claim once with the founder-led opening and once with a customer-quote opening, keeping format, CTA, publishing window, and offer constant. Compare the 72h save rate before calling the angle itself the cause.”

This is an example of required specificity, not a reusable output template.

Risk categories to check (in priority order):

1. TENANT ISOLATION — Most critical for scraping modules
   - Can competitor data from account A ever appear for account B?
   - Are all DB queries scoped by accountId AND campaignId?
   - Does shared-profile-store.ts enforce per-account isolation on reads and writes?
   - Are any in-memory caches or Maps shared across accounts?

2. AUTH & ROUTE PROTECTION
   - Do all routes in analysis-routes, competitor-routes, data-acquisition-routes, dominance-routes, reviews-tiktok-routes have authMiddleware?
   - Is requireCampaign (or equivalent) applied before any data is returned?
   - Any endpoints accessible without authentication?

3. ERROR DISCLOSURE
   - Do any catch blocks return err.message directly to the client?
   - Are internal DB errors, proxy details, or scraper stack traces visible in responses?

4. PROXY CREDENTIAL SAFETY
   - Does proxy-pool-manager.ts ever log proxy usernames or passwords?
   - Are credentials redacted before appearing in logs or error responses?
   - If a proxy fails, does the error message contain credential details?

5. SILENT FAILURES in scraping pipeline
   - Do profile-scraper, tiktok-scraper, tiktok-apify-scraper, reviews-scraper have bare catch{} blocks that silently discard failures?
   - If a scrape fails, is the failure surfaced (logged, flagged, or returned as degraded) rather than silently returning empty data?

6. UNBOUNDED QUERIES
   - Are all DB queries in shared-profile-store.ts and data-acquisition.ts bounded with .limit()?
   - Can any query return an unlimited number of rows based on account data volume?

7. INPUT VALIDATION on routes
   - Are competitorId, campaignId, accountId validated (type, format, ownership) before use?
   - Can a caller pass arbitrary IDs to access data they don't own?

8. RATE LIMITING on scraping
   - Beyond the rate-limiter.ts (already clean), do the scrapers themselves enforce per-account scrape frequency?
   - Can a single account trigger unlimited scrape jobs?

## Objective

Make Watchtower detect real competitor and market changes over time, store them as structured events, and verify that the complete flow works on a real campaign using real scraped competitor data.

The required flow is:

Competitor scraping → historical snapshots → old-vs-new comparison → classified market change event → campaign-visible Watchtower signal.

This session is limited to data collection, retention, change detection, and verification. Do not build the AI interpretation layer or user recommendations yet.

## Phase 3 — Implementation

### A. Historical competitor snapshots

Implement append-only snapshot history for each competitor fetch.

Requirements:

* Every fresh successful fetch creates a timestamped historical record.
* Existing callers that need the latest snapshot continue to work.
* Snapshot reuse must be marked explicitly.
* Fresh fetches and reused snapshots must never be indistinguishable.
* Store source timestamps and fetch timestamps separately where applicable.
* Add configurable retention: 90 days full-fidelity history, with a documented later compression path if compression is not implemented in this session.
* Do not silently overwrite prior competitor state.

### B. Watchtower Orchestrator

Create or complete the Watchtower orchestration layer.

After a successful competitor fetch cycle:

1. Load the newest snapshot.
2. Load the immediately previous comparable snapshot.
3. Run the existing diff primitive where possible.
4. Materialize detected differences as structured market change events.
5. Attach both snapshot IDs and evidence references.
6. Associate the event with the correct competitor and campaign.

The orchestrator must work with real campaign scraping results, not only direct test calls.

### C. Deterministic classification

Initial classification must be code-based, not AI-based.

Use verified available data only.

Expected categories where supported:

* `offer_language_change`
* `posting_frequency_shift`
* `dominance_shift`
* `phrase_saturation_change`
* `pricing_page_change`
* `engagement_pattern_shift`
* `competitor_profile_change`

Severity model:

* Non-trivial offer change: candidate alarm.
* Confirmed pricing-page change: candidate alarm.
* Dominance delta of at least 10 points: watch.
* Posting frequency shift beyond one standard deviation of that competitor’s own trailing baseline: watch.
* New phrase family repeated across at least three competitors: watch.
* Minor changes: info.

Do not lower any threshold to force events to appear.

If the available real data cannot honestly support one of these categories, mark it UNAVAILABLE and do not fabricate it.

### D. Two-fetch validation

A candidate alarm must not become a confirmed alarm on the first observation.

Required behavior:

* First observation: candidate event with `validated_at = null`.
* Same material change confirmed in the next independent fresh fetch: promote and set `validated_at`.
* Reversion before confirmation: do not promote.
* Snapshot reuse does not count as a second confirmation.
* Manual duplicate execution does not count as an independent confirmation.

### E. Failure behavior

All failures must be loud and structured.

Required tags include:

* `WATCHTOWER_ORCHESTRATOR_FAILED`
* `COMPETITOR_SNAPSHOT_WRITE_FAILED`
* `COMPETITOR_DIFF_FAILED`
* `MARKET_EVENT_PERSIST_FAILED`
* `SCRAPING_FRESHNESS_UNVERIFIED`
* `SCRAPING_SNAPSHOT_REUSED`
* `SCRAPING_SOURCE_FAILED`

A competitor-specific failure must not corrupt the full campaign cycle.

No silent catches, no `|| null` swallowing, and no fake successful state.

PHASE 2 — Implement the three wiring changes

A. Plan lineage at publish time

At the point a content_calendar_item is created, persist the lineage tags from the plan that generated it: content_type, hook_style, angle, mix_bucket (problem/education/proof/conversion), planned_slot (day+time), and campaign_id (the campaign that owns the plan). New column(s) via a proper numbered migration, fail-closed consistent with existing schema-floor checks.
At publish time, propagate these tags onto whatever record represents the published post (or a linking table if that's the cleaner shape — justify choice in Phase 1 findings).
Posts published outside a plan (user manual publishes) get tagged unplanned explicitly — measured but excluded from plan scoring.
Failure to attach lineage does NOT block publish — log PUBLISH_LINEAGE_MISSING loudly with the reason. Never silent.

B. Revive outcome-tracker.ts to READ, not create

Replace the stub with a real reader that pulls from the existing outcome_snapshots populated by Meta webhooks — do NOT build a parallel ingestion pipeline (this is the key P-0 finding: infrastructure exists, connection missing).
Join outcome_snapshots to published posts via the lineage from (A). Snapshots that predate the lineage change stay legacy — flagged, not deleted.
Expose a per-post query surface: given postId, return the last-known metrics with their capturedAt timestamps. Missing metrics return null (not zero) — honest boundary per performance-loop-spec §1.
Loud log on join failures: OUTCOME_SNAPSHOT_ORPHAN with the reason. Never silent.

C. Per-post revisit scheduler (the shared component)

New scheduler that revisits each published post at 24h / 72h / 7d after publish, calls the existing metric fetch, and writes a fresh outcome_snapshot row (append-only history — do not overwrite prior rows).
Same scheduler serves the future Watchtower engagement-spike sense (competitor post revisit). Design the job signature so both callers (own posts, competitor posts) share the code path with different targets — do not fork.
Fail-closed: revisit failure = one log line (REVISIT_FAILED with post id + reason), skip this cycle, try again next scheduled hit. Never retry storms.

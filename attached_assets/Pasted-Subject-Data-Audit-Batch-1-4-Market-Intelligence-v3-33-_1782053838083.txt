AUDIT INSTRUCTIONS:

Do a thorough line-by-line review of each file (read every line, NOT a keyword scan). Focus on these DATA-specific risks:

1. TENANT ISOLATION (most important)
   - Is every scrape, fetch, and snapshot scoped to a single account/campaign?
   - Can data from one account ever leak into another's market intelligence?
   - Does isolation-guard.ts actually enforce isolation, or is it bypassable?
   - Are there any module-global mutable arrays/objects shared across requests (like the Offer Engine F1 cross-tenant bug)?

2. DATA QUALITY & GROUNDING
   - When scraped data is weak, thin, or from a single source, is it flagged (evidenceQuality / confidence) or silently treated as solid?
   - Does confidence-engine.ts produce honest confidence, or can it fake high confidence on poor data?
   - Are freshness/staleness timestamps validated (no NaN / bad-date → wrong age)?

3. SCRAPE SAFETY
   - Is website-scraper.ts protected against SSRF (private IPs, internal hosts, DNS rebinding)?
   - Are scrape volume caps (scrape-volume-cap.ts) actually enforced, or bypassable?
   - Is token-budget enforced before expensive AI calls?

4. SILENT FAILURE
   - Any empty catch {} or .catch(() => []) that swallows scrape/parse errors?
   - If a data source fails, is it logged and flagged, or silently dropped while the engine continues on partial data?

5. LLM OUTPUT SAFETY
   - Any JSON.parse on LLM output without try/catch and without schema (Zod) validation?
   - Is prompt-safety.ts effective against prompt injection from scraped competitor content?

6. UNBOUNDED QUERIES
   - Any DB query without .limit() that could load huge result sets?

7. ERROR DISCLOSURE
   - Do routes.ts / admin-routes.ts return raw err.message to the client?
   - Are admin-routes properly gated behind admin auth?
